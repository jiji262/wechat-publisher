# 标题:读者在信息流里的第一次判断

标题不是摘要,是读者在信息流里决定点不点的那一行。技术文章的标题先让人认出对象和问题,
再让人判断这篇值不值得读。完整候选流程在 SKILL.md 阶段三;本文件给判据、角度和核对清单。

## 四个成分

- **具体对象**:产品、版本、协议、报错、命令、数字。读者先要判断这篇和自己有没有关系。
- **变化或问题**:这次发生了什么、哪里不对、要回答什么。没有变化和问题,标题就只是名词堆叠。
- **读者能拿走的判断**:原理、做法、取舍、边界。技术读者点开文章,通常是为了弄懂或做决定。
- **可信度**:版本号、时间、数据、来源。可信度让标题不靠形容词成立。

不是每个标题都要四样齐全,但至少要有一个具体对象和一个明确角度。缺少对象时,
读者只能靠"深度""干货"这类词猜内容,标题就退回了模板。

## 五种起法

1. **事实型**:对象 + 关键数字、版本或变化。适合榜单、benchmark、融资、财报、模型能力。
2. **机制型**:对象 + 它怎么运作、为什么这样设计。适合拆解框架、协议、Agent 架构、SDK。
3. **问题型**:读者真会问的问题 + 正文给出的答案方向。适合争议、真假难辨、产品变化。
4. **取舍型**:两个方案在什么条件下各自合适。适合选型、对比、反常识。
5. **复盘型**:事件 + 根因或代价。适合翻车、处罚、安全事件、商业事故。

一篇通常只用一种起法。需要两种时,让主角度落在前半句,后半句补对象或条件。
这些起法只给角度,不给可以照抄的句式。

## 长度与显示

- 目标 14–24 个汉字。手机信息流里,超过 26 个汉字容易被截断。
- 把对象和关键判断放在前 16 个字内。读者扫不完一整行。
- 一个标题最多一个冒号。冒号右边要给出新信息:对象、数字、结论或条件,不能只是悬念。
- 不用书名号和引号装饰。只有引用真实报错、原文或书名时才用。
- 不用表情符号和叹号。技术文章的情绪由事实和后果承担。

## 反模式

| 模式 | 为什么不行 | 改成 |
|---|---|---|
| 悬念冒号 | 冒号前铺情绪,冒号后才给信息 | 把结论或对象写进冒号前 |
| 否定对照 | 先替读者设一个错误认知,再翻案 | 直接写事实和结论;真有误解时写出处 |
| 数量模板 | 把文章钉死成清单体,数字常常不是新闻 | 写具体对象和变化;数字本身是新闻时才放前面 |
| 夸张动词/拟人 | 用"收编""杀疯""封神"代替真实动作 | 写哪个主体做了什么,结果是什么 |
| 空泛大词 | "底层逻辑""认知升级""干货"不指向具体内容 | 换成可核对的对象、版本、结果 |
| 问句钩子 | 问题只是答案的前缀,正文没有真回答 | 陈述句;正文真的回答一个问题时才用问句 |
| 蹭热点/流行语 | 标题和文章的技术对象脱节 | 写技术对象和读者任务 |

## 选择顺序

**准确 > 清晰 > 具体 > 有趣。**

- **准确**:标题点名的对象、版本、数字和结论与正文一致。标题许诺的内容正文必须兑现。
- **清晰**:读者一眼看出这是原理、排障、对比、复盘还是选型。
- **具体**:优先名词、数字、版本和动作,少用抽象评价。
- **有趣**:排在前三项之后。靠对象本身的冲突和后果,不靠悬念、夸张和流行语。

## 发布前核对

- 标题里的产品名、版本号、数字在正文出现过,含义一致。
- 标题许诺的数字、结论或对比,正文有对应段落;第一节就要开始兑现。
- 标题没有替读者设定一个正文没有证明的错误认知。
- 小标题连起来能复述标题许诺的主线。
- 和最近 3 篇标题不是同一句式;同一系列的文章除外。
- `python3 scripts/title_check.py "<候选>"` 没有警告;有提示就逐条确认,不机械清零。
